## 设计与实现

### 需求与功能结构

必需功能包括基础四则运算、复合表达式、数据库历史以及按 ID 删除。除了界面截图，还需要证明后端停止时不能计算，以及刷新和重启不会使数据库历史丢失。

![功能结构图](images/functional-structure.png)

*图 18　计算器系统功能结构图*

扩展包括分页、键盘快捷操作、算式复用、匿名浏览器历史隔离、访问来源、中英文切换、自适应挂件、动效、音乐和云指标。当前没有账号登录、科学计算或清空全部历史，不将这些功能作为已完成项。

### 总体架构

![架构图](images/architecture.png)

*图 19　Vue、Express、SQLite 与阿里云部署架构*

Vue 负责输入和展示；Express 负责验证、解析、计算与数据库操作。开发环境由 Vite 将 `/api` 转发到后端；生产环境由 Nginx 托管静态前端并代理相同路径。前端无需把后端 IP 写入组件，两端仍保持独立应用的职责。

### 技术选型与原因

| 技术 | 使用位置 | 选择原因 |
|---|---|---|
| Vue + Vite | 前端组件与构建 | 响应式状态便于展示请求结果和历史，组件可以分别管理播放器、挂件与状态卡片；构建后为独立静态文件 |
| Node.js + Express | 后端 HTTP 服务 | 路由与计算、存储模块可以分开测试，使用明确的 JSON 接口连接前端 |
| SQLite | 历史持久化 | 单文件数据库适合本次小型项目，无需再运行独立数据库服务；后端首次启动自动初始化 |
| 自写递归下降解析器 | 算式处理 | 四则运算语法范围明确，能够直接控制优先级、错误信息和输入边界，避免执行用户代码 |
| Nginx + systemd | 阿里云部署 | 同源 HTTPS 入口、静态资源托管、接口反向代理与后台服务管理各有明确职责 |

### 前端设计

`App.vue` 管理算式、加载、结果和历史状态，只展示 API 返回的答案。成功新增或删除后重新读取历史，并使用请求序号防止较早的响应覆盖较新的列表。响应式布局、可访问名称和键盘操作覆盖主要控件。

播放器、鲸鱼挂件、动效和状态卡片分别由组件管理，不参与核心运算。背景支持暂停及系统减少动态效果；localStorage 只保存语言、位置和播放偏好，不能替代后端历史数据库。

### 后端模块与接口

| 方法与路径 | 职责 | 成功响应 |
|---|---|---|
| POST `/api/calculations` | 校验、计算并保存 `{expression}` | 201，返回已保存记录 |
| GET `/api/calculations?limit=20&offset=0` | 查询当前浏览器分页历史 | 200，items 与 total |
| DELETE `/api/calculations/{id}` | 删除本人身份下指定 ID | 204，无响应体 |
| GET `/api/health` | 基础连通检查 | 200 |
| GET `/api/status` | 数据库检查及系统指标 | 200 |

请求 `{"expression":"(1+2)*3"}` 后，成功响应包含 success、UUID id、expression、字符串 result（"9"）、ISO createdAt 和来源信息。错误返回 success:false 与安全消息。非法算式使用 400，不存在或不属于当前身份的删除使用 404；错误内容类型为 415，过大请求为 413，超限为 429，内部异常返回通用 500。

`calculator.js` 负责解析，`history-store.js` 负责 SQLite，`client-info.js` 读取请求来源，`protection.js` 处理 HTTP 防护，`system-status.js` 采样，`app.js` 组织路由，`server.js` 负责配置与启动。

### 数据库设计

| 字段 | 类型 | 含义 |
|---|---|---|
| id | TEXT 主键 | 服务端生成 UUID |
| expression | TEXT 非空 | 成功提交的原始算式 |
| result | TEXT 非空 | 格式化结果 |
| created_at | TEXT 非空 | UTC ISO 时间 |
| client_info | 可空 TEXT | IP、估算归属地、设备等 JSON |
| owner_id | 可空 TEXT | 服务端签发的匿名浏览器身份 |

数据库使用 WAL，SQL 使用预编译绑定参数，并有按身份和时间查询的索引。新字段通过迁移添加，保留旧行。后端完成入库后才报告成功；错误算式不保存。删除条件包含 ID 和所属身份，前端随后重新查询。

生产数据库放在发布目录外，代码更新不会重建历史。清除 Cookie 不会删除数据库，但新身份不能访问旧身份的记录。

### 解析器设计

分词器只接受数字、四则运算符和括号，将 ×、÷、− 规范化。数字支持小数和科学记数法。递归下降语法如下：

```text
sum     := product (("+" | "-") product)*
product := unary (("*" | "/") unary)*
unary   := ("+" | "-") unary | primary
primary := number | "(" sum ")"
```

每层调用优先级更高的一层；括号递归进入 sum。结束时必须消费全部 token，拒绝多余操作数与错误括号。算式限制 200 字符，计算过程检查有限值及除零。不执行 eval、Function 或用户通用代码。

### 交互与异常

计算流程为输入 → POST 算式 → 后端验证计算 → SQLite 保存 → 返回记录 → 展示结果 → GET 更新历史。删除流程为点击垃圾桶 → DELETE 指定 ID → 数据库真实删除 → 204 → GET 更新列表。

解析失败返回 400 并跳过写库；网络失败显示连接错误；写库失败不报告“已保存”。界面保留的旧结果只代表已有记录，不表示离线情况下仍可计算新表达式。

### 来源与防护

新记录包含提交请求的 IP、离线估算归属地及设备标签。本机和内网地址明确分类；归属地不能代表精确位置，User-Agent 也可能被修改，因此不用于身份认证，更不将它们描述为账号登录审计。

匿名 Cookie 使用签名、HttpOnly、SameSite=Strict，生产环境加 Secure；接口拒绝跨站来源，写请求要求校验头，JSON 限制 2 KB，按 IP 限流。SQL 参数绑定避免用户输入变成 SQL。公共指标接口只返回聚合状态。上述检查覆盖常见滥用，不能宣称为完整渗透测试。

## 关键代码

### 前端只发送算式

来自 `frontend/src/App.vue`：

```js
const response = await fetch('/api/calculations', {
  method: 'POST',
  headers: {'Content-Type': 'application/json', 'X-Calculator-Request': '1'},
  body: JSON.stringify({expression: expression.value}),
  signal: AbortSignal.timeout(5000),

```

请求不包含前端算出的结果；五秒超时限制等待，新答案由后端产生。

### 后端计算后保存

来自 `backend/src/app.js`：

```js
const calculation = calculate(request.body?.expression);
response.status(201).json({success: true,
  ...store.save(calculation, readClientInfo(request), request.ownerId)});
```

先解析，再保存，最后发送成功；解析异常被转换为 400。

### 乘除优先级

来自 `backend/src/calculator.js`：

```js
function product() {
  let value = unary();
  while (peek() === '*' || peek() === '/') {
    const operator = tokens[index++].type;
    const right = unary();
    if (operator === '/' && right === 0) throw new CalculationError('不能除以零');
    value = finite(operator === '*' ? value * right : value / right);
  }
  return value;
}
```

操作数经 unary 读取，因此支持 `3*-2`；sum 调用 product，确保乘除先于加减。

### 按身份真实删除

来自 `backend/src/history-store.js`：

```js
const ownedRemove = database.prepare(
  'DELETE FROM calculations WHERE id = ? AND owner_id = ?');
```

绑定参数控制查询结构，ID 与身份同时匹配。成功响应后前端调用 loadHistory，而非只把页面元素隐藏。

5. 检查 HTTP 跳转 HTTPS、健康接口、云状态及实际计算、历史读取和删除。评阅期间保持公网服务在线。

## 学习体会

### 实际问题与解决过程

| 问题 | 排查依据 | 解决方式与验证 |
|---|---|---|
| 旧版历史没有区分访问者 | 公网列表和删除接口缺少所属身份过滤，记录中的 IP 等来源字段可能被其他访问者查看 | 增加服务器签名的匿名身份，查询和删除同时约束 `owner_id`；用两个独立身份验证互相不可见，跨身份删除返回 404 |
| 首次加载时多个接口可能竞争历史身份 Cookie | 页面同时查询历史和服务器状态；若两路都为新浏览器签发身份，响应顺序可能影响后续历史归属 | 让 `/api/status` 只提供公共聚合指标，不创建历史 Cookie；回归测试确认状态响应没有 Set-Cookie，历史接口继续管理身份 |
| 本机隔离测试刷新后看不到原测试记录 | 数据库记录仍在，但同一域名下不同端口的开发服务会共用 Cookie；需要先区分数据丢失与身份变化 | 在独立 HTTP 客户端中保留测试 Cookie 和同一签名密钥，真实停止、启动后端后再次查询；八条保留，按 ID 删除后再重启仍有七条 |

这几项核验使我更重视“页面状态、浏览器身份和数据库状态”之间的区别。排查历史异常时，应同时检查接口响应、身份是否变化和数据库是否仍有记录，再决定修改位置；只看页面列表不足以判断持久化是否失效。

### 对前后端分离的理解

本项目最核心的学习点是通过接口落实职责划分。前后端分别放在文件夹中只是组织方式；真正需要回答的是每项操作由谁负责。计算器前端描述请求并展示结果，后端判断算式是否合法、执行计算并保存数据。这一边界使界面变化能够与计算规则变化分别进行。

API 是两端协作的约定。`{"expression":"(1+2)*3"}` 的语义清晰，成功与失败应通过状态码和字段一致表达。这样的约定也有助于定位问题：结果不正确时检查解析器，记录不正确时检查保存和查询，服务不可访问时检查网络和部署配置。如果以后添加另一个客户端，可以复用相同的后端能力。

历史记录让我进一步理解数据归属。组件中的列表只是临时展示状态，SQLite 中的记录才会跨刷新和重启保存。删除只有在数据库真正移除对应记录时才算完成。写操作后重新查询能够让页面以后端状态为依据。浏览器存储适合保存语言等偏好，用它代替数据库历史则会偏离本作业的架构目标。

安全解析说明后端不能依赖界面输入限制。外部请求可能绕过数字键盘，因此后端仍要验证符号、长度和运算规则。分词器和小型语法让合法范围明确，不必执行用户代码。一元符号、乘除、加减和括号分层后，优先级也更容易解释和测试。

开发与部署的连接方式同样体现分离思想。相对 `/api` 地址在本机由 Vite 代理，在生产由 Nginx 代理；两端仍保留独立代码、依赖和启动流程。配置、密钥和数据库的生命周期不能跟随一次代码发布结束，否则更新可能使历史丢失或身份发生变化。

后续我会优先考虑精确小数运算、历史搜索、接口文档和更系统的无障碍检查。如加入账号同步，就需要真正的认证方案，不能把 IP 或浏览器标签当作身份。装饰媒体也应保持可关闭，使核心计算与记录始终清晰可用。
